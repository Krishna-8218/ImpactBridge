# 06 — Team workflow, ownership, and the AGENTS.md to ship

## How 8 people avoid each other

The contract layer removes the *integration* bottleneck. This section removes the *merge*
bottleneck. Every shared file is either owned by one person or structured append-only.

| Area | Files | Owner |
|---|---|---|
| Platform | `src/contracts/_kit.ts`, `src/server/route.ts`, `src/lib/api-client.ts`, `AGENTS.md` | **Owner A** — sole writer |
| Auth | `src/lib/auth.ts`, `auth-client.ts`, `(auth)/*`, `onboarding/*` | **Owner B** |
| Schema + migrations | `src/db/schema/*`, `drizzle/*`, running `migrate` | **Owner C** |
| Design system | `src/app/globals.css`, `components/ui/*`, `AppShell` | **Owner D** |
| Features ×2–3 | one contract file + one server file + one route dir + its pages, each | **E, F, G** |
| Integration & deploy | Vercel, env vars, Google console, demo script | **Owner H** |

Append-only files — never restructured, only added to: `src/contracts/index.ts`,
`src/db/schema/index.ts`. One import line per feature, so two people adding features in
the same hour edit two different lines.

### Feature workflow (the whole thing, in order)

1. **Contract first.** Write `src/contracts/<feature>.ts` with schemas **and** a `mock`.
   Register it in `index.ts`. Commit and push immediately — this unblocks everyone.
2. **Routes next.** `src/app/api/<feature>/route.ts` with `defineRoute(contract)` and
   **no handler**. Push. The endpoint is now live and returns realistic data.
3. **Split.** Frontend builds against `api.<feature>.*` — real HTTP, real types, real
   loading and error states. Backend writes `src/server/<feature>.ts` against the same
   contract.
4. **Land.** Backend adds the handler argument. Frontend changes nothing. Done.

Steps 1–2 take about ten minutes and are what make steps 3–4 parallel. Do not skip them
and "just build the real route" — that's how integration debt starts.

## `AGENTS.md` — ship this text

`CLAUDE.md` is one line: `See AGENTS.md.` Single source of truth, both agents read it.

````markdown
# AGENTS.md

Hackathon starter: Next.js 16 (App Router) · Better Auth · Drizzle · Neon Postgres ·
Tailwind v4 · shadcn/ui. Eight people work in this repo simultaneously. The rules below
exist so their work merges cleanly and integrates on the first try.

## Commands
```bash
npm run dev            # localhost:3000 — ALWAYS port 3000 (Google OAuth callback is registered for it)
npm run build
npm run typecheck      # tsc --noEmit — run before every commit
npm run lint
npm run db:generate    # drizzle-kit generate  → writes SQL into drizzle/, commit it
npm run db:migrate     # drizzle-kit migrate   → SCHEMA OWNER ONLY, shared database
npm run db:seed
npm run auth:generate  # npx auth@latest generate → regenerates src/db/schema/auth.ts
```

## Hard rules

1. **Never create an API route without a contract.** Every endpoint is a
   `defineContract` in `src/contracts/<feature>.ts`, registered in
   `src/contracts/index.ts`. Route files are two lines and contain no logic.
2. **Never write `fetch('/api/...')` in a component.** Use `api.<feature>.<op>()` from
   `@/lib/api-client`. Typed, validated, and it can't drift from the server.
3. **Never run `drizzle-kit push`.** Shared Neon database — `push` silently drops other
   people's columns. Use `db:generate` + `db:migrate`, and only the schema owner migrates.
4. **Never hand-edit `src/db/schema/auth.ts`.** It is generated by `npm run auth:generate`
   from `additionalFields` in `src/lib/auth.ts`. Edit the config, regenerate.
5. **Never make a Better Auth `additionalFields` entry `required: true`.** Google sign-in
   cannot supply custom fields, so a required field breaks Google sign-up. Optional +
   `defaultValue`, collected in `/onboarding`.
6. **Never set `input: true` on an authorization field.** `systemRole` is `input: false`.
   Anything `input: true` can be set by anyone POSTing to the sign-up endpoint.
7. **Never import `@/lib/auth` as a value in a client component.** Type-only import, or
   the DB driver ends up in the browser bundle.
8. **Never install another UI or data-fetching library.** shadcn components live in
   `src/components/ui`. The API client is `src/lib/api-client`.
9. **Never upgrade `drizzle-orm`.** Pinned to `0.45.2`; `@better-auth/drizzle-adapter`
   peers `^0.45.2`. The Drizzle docs' `@rc` instruction installs the v1 beta and breaks it.
10. **Never restructure `src/contracts/index.ts` or `src/db/schema/index.ts`.** Append one
    line. Eight people edit these files.

## Conventions

- **Response envelope** — every route returns `{ ok: true, data, source }` or
  `{ ok: false, error: { code, message, fields? } }`. Set by `defineRoute`; don't
  hand-roll a `Response.json`.
- **Errors** — handlers `throw new ApiError('NOT_FOUND', 'Project not found')`. Codes:
  `VALIDATION_ERROR` `UNAUTHORIZED` `FORBIDDEN` `NOT_FOUND` `CONFLICT` `RATE_LIMITED`
  `INTERNAL`.
- **Dates cross the wire as ISO strings**, never `Date`. Contracts use `z.string()`.
- **GET inputs come from the query string** → use `z.coerce.number()` for numbers, never
  bare `z.number()`.
- **For query-string booleans use `z.stringbool()`, NEVER `z.coerce.boolean()`.**
  `z.coerce.boolean().parse('false') === true` (plain JS truthiness on a non-empty string),
  so `?done=false` silently filters to done-only. Verified against zod 4.4.3.
- **`params` is a Promise** in Next 16. `defineRoute` awaits it for you; if you write a
  raw handler, `await params`.
- **Business logic lives in `src/server/<feature>.ts`**, never in a route file.
- **Auth in server components**: `await auth.api.getSession({ headers: await headers() })`.
  Middleware only does an optimistic cookie check — it is not the authorization boundary.
- Node runtime everywhere. Never `export const runtime = 'edge'`.

## Working on the frontend

The route you need already exists and returns realistic mock data. Just call it:

```tsx
const { projects } = await api.projects.list({ status: 'active' })
```

- `?__mock=1` or the `x-mock: 1` header forces mock data for one request — use it when a
  backend teammate is mid-refactor on that endpoint.
- `?__mock=error` forces an error response. Build your error state with it.
- `MOCK_DELAY_MS` (default 250) makes loading states visible. Build skeletons.
- Render `<MockBadge source={...} />` on any page whose main data comes from an endpoint,
  so nobody demos mock data believing it's live.
- Browse every endpoint at **`/dev/api`**.

## Working on the backend

1. Read the contract. It is the spec — do not change its shape without telling the
   frontend owner, because their UI is already built against it.
2. Write the logic in `src/server/<feature>.ts`.
3. Add it as the second argument to `defineRoute`. That's the whole switch.
4. In dev, a handler whose output doesn't match the contract returns
   `CONTRACT_VIOLATION` with the mismatch logged. That error means your code is wrong, not
   the framework.

## Adding a user profile field

1. Add it to `additionalFields` in `src/lib/auth.ts` — `required: false`, with a
   `defaultValue`, and `input: false` if it's security-relevant.
2. `npm run auth:generate` → `npm run db:generate` → tell the schema owner to migrate.
3. Add the field to the `/onboarding` form.

## Definition of done

`npm run typecheck` passes · the contract and route are committed and pushed · a page
consuming it renders in both mock and live mode · empty, loading and error states exist ·
no new dependency without asking the platform owner.
````

## Deploy

### "Where does the backend get deployed?" — it doesn't, separately

This question comes up on every team; answer it once, here.

The Next.js app **is** the backend. One `git push` produces one deployment containing
both halves:

```
ONE Vercel project
 ├── static assets + prerendered pages     → CDN
 └── app/api/**/route.ts + server components → Vercel Functions
                                                │  DATABASE_URL
                                                ▼
                                        Neon Postgres (managed service,
                                        provisioned in a dashboard, never deployed)
```

Verified: https://vercel.com/docs/frameworks/full-stack/nextjs — "framework-aware
infrastructure enables automatic creation of Functions for SSR"; Route Handlers run as
Vercel Functions.

Consequences the team should rely on:
- The API is same-origin (`/api/projects`). The typed client uses **relative URLs** —
  there is no `NEXT_PUBLIC_API_URL`, and no staging/prod URL mismatch to get wrong.
- **No CORS configuration, ever.**
- Better Auth cookies are first-party — none of the cross-site cookie failure modes.
- One set of env vars, one deployment to watch.

Constraint: Vercel Functions are stateless and scale to zero — no in-memory session
store, no background workers, no WebSocket server. Nothing in this starter needs any of
those (Better Auth keeps sessions in Postgres). If a feature ever does, that is the
moment this decision gets revisited — not before.

**Alternative host**, if an always-on Node server is wanted (Railway / Render / Fly / VPS):
set `output: 'standalone'` in `next.config.ts` + a Dockerfile; `node server.js` serves the
same combined app. Still one deployment, still one origin. No repo changes.

### Day-one checklist

Vercel, one project, `main` auto-deploys. Owner H sets the env vars and adds the
production callback URL to Google. Do this on **day one, with a hello-world page** — a
first deploy attempted at hour 40 is how teams lose hackathons.
